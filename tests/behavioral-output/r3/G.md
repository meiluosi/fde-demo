先说判断：客户这两条限制不是障碍，是这次 Demo 的设计前提。真实数据不能丢（红线一），但“真实数据”不等于“数据要到我们这里来”，所以路径应该是让系统去数据那边，而不是让数据来系统这边。

**有两件事先划掉**
- 把数据脱敏后传到外部 API 跑一遍：客户已经明确说不行，不要靠“脱敏了应该没事”绕过。除非客户书面授权，否则这条不存在。
- 用玩具数据或公开数据演，然后说成“客户数据 Demo”：这是造假，不能做。

**按保真度从高到低，下周能走哪条取决于客户环境**
1. **在客户内网/客户设备上本地跑**，用能离线部署的模型，数据不出域。这是首选，也是最能同时满足“真实数据”“不出内网”“不调外部 API”的做法。
2. **客户现场自带样本，当场脱敏，用你们的离线环境跑**，用完不留存。需要客户明确同意把样本放进你们带去的设备。
3. **低保真预演**：客户只给脱敏后的字段清单和分布，你们按真实结构生成合成数据，在本地模型上跑。口头和书面都要标“合成”，只能当预演，不能当作验证“在你们真实数据上有效”，也不能算数据轴已验证。
4. **推迟 Demo**，把这次改成数据授权与环境准备的沟通会。拿不到二十条脱敏数据，本身就是重要发现，要写进简报和复盘，不要悄悄换成合成数据。

我倾向先争取 1 或 2，退而求其次用“3 加一个明确的 ask（拿真实样本和内网环境）”，实在没有合规路径就走 4。下周必须有一场会，不等于下周必须有一场“真实数据 Demo”。如果只能走 3，这场会的目标权重应该放在“信任与权限”，ask 就是拿到走 1 或 2 的授权。

**设计上要提前处理的几点**
- “不调外部大模型 API”要查全：向量化、OCR、联网检索、遥测上报、依赖包自动更新，是否都离线。到现场发现某个组件偷偷联网，比没做更糟。
- 本地模型通常比你们平时用的 API 模型弱。技术轴只能判断“本地模型在这批数据上做到什么程度”，不能拿外部模型的效果替客户的约束作担保。失败样例要用本地模型真实跑出来。
- 最简替代方案（规则、关键词、客户现有做法）在离线条件下可能就够用，要在同一批问题上对照，别只演大模型。
- 现场推理慢的话可以预跑，但要登记并明说“这是昨天在你们环境里跑的结果”。现场跑失败不能悄悄换成预跑。
- 数据来源、授权人、脱敏方法、留存方式都要记下来；不给无关人员看客户数据。守门人（IT/合规/数据）要在场或事先签字。

**我需要你回答的 3 个问题，答案会直接决定走哪条路**
1. 客户内网里有没有你们能用的运行环境（服务器、GPU、客户的电脑），以及允许你们带离线模型或软件进去吗？有就走 1；没有就看能否走 2；都没有就是 3 或 4。
2. 谁能批准“用真实数据”，批到什么程度？比如只能在客户设备上看、能否现场自带 20 条样本脱敏后使用、用完是否必须删除？这位授权人和数据守门人下周会到场吗？
3. 这次要验证的唯一主张是什么、最痛的一步是哪一步、使用者会不会到场动手？这决定演什么、成败信号怎么登记。

**答案回来之前，我先把能确定的和待补的列出来**

已能确定：
- 数据来源这一节写“客户内网真实数据 / 现场自带 / 合成”三选一，并同步写合规状态。
- “本次不展示”：不展示任何联网能力，不展示外部模型效果。
- ask 的方向：真实脱敏样本（写清份数、类型）、内网环境访问、2 位使用者各若干分钟、一个具体期限；同时记一下过去同类数据申请要等多久。
- 失败样例至少 2 个，来自本地模型在真实难例上的实际表现。

待确认或待测：
- 客户环境与授权范围（问题 1、2）。
- 唯一主张、最痛的一步、基线（问题 3）。
- 本地模型在代表性样本上的表现、与最简方案的对照。
- 预跑项与披露话术。
- 成败信号：先登记要观察的行为，不写准确率阈值。如果客户还没有验收标准，把“让他说出怎样才算够用”设计成现场一个环节。
