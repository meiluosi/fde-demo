# 七条原则

“用客户的真实数据”已升为红线一，见 [redlines.md](redlines.md)。其余原则如下，每条给出做法、常见失误和需要的兜底。

## 一、演示最痛的一步
不是最容易实现的那一步。注意力有限，所以把时间花在客户日常最难受的环节上。依据来自 fde-ramp 活动表、fde-problem-framing 定义卡里被验证过的瓶颈；若还没被验证，把“这一步是不是最痛”本身当作价值轴要检验的假设。
- 失误：选了最容易跑通的环节；选了领导关心而使用者不痛的环节。

## 二、让客户自己动手
只看你演示，客户的体会有限；让他亲手操作、用自己的材料试一遍，说服力会大得多。
- 兜底：他一定会上传一个你没测过的文件。提前准备：只读沙盒、文件类型提示、出错时的解释路径。真失败了，按原则三当作展示失败的机会，当场记录文件特征，不要尴尬跳过。
- 记录：他选了哪个文件、为什么选、有没有人提示。未经提示自己选，是强价值信号。
- 动手时出 bug：如实说是我方程序的问题，不与模型的预测误差或结论混为一谈；记录现象，限时修复并回归。事前在同样环境、同类输入上冒烟测试一遍。

## 三、主动展示失败
准备两三个系统会出错的例子，主动讲：“这类情况现在还处理不好，原因是……我们的想法是……”这看似削弱演示效果，实际会提高可信度。只展示成功的演示，有经验的客户会怀疑你有所保留。
- 失败样例来自真实数据的难例，不来自编造。每个样例写：现象、已知原因、下一步想法。
- 失误：把失败样例讲成“已解决”；只讲一个无关紧要的小错。

## 四、一次只讲一个主张
Demo 最常见的毛病是想展示的东西太多。三个功能都演示一遍，客户什么都记不住。选一个讲透。
- 其余能力写进“本次不展示”，避免被现场牵着走；被问到就说“后续单独演示”。
- 与红线二不冲突：主张只有一个，案例是中等难度的典型件。

## 五、现场可改
客户提出“能不能把这个字段也提取出来”，你能在十分钟内改好再跑一遍：这一刻往往比前面的讲解更有说服力。它证明的是响应速度，而不只是技术。
- 边界必须事先写好：能改的是字段清单、提示词、显示顺序、配置这一层；不能改的是架构、系统接入、权限。
- 十分钟改不好就坦白，约好时间，不硬撑；改完回归跑一遍已演示的案例，防止顺手弄坏别处。
- 每次现场改动记入记录表：谁提的、改了什么、耗时、结果。

## 六、留一个明显的缺口
留一处显而易见、容易被提意见的地方。客户提出后你当场改好，他就从旁观者变成了共同作者。参与过修改的人，往往更愿意为结果背书。
- 缺口必须真实存在、已知、低风险（如暂不支持某类案件的次要字段），不能是核心准确性问题，更不能故意制造。
- 被客户改过的地方，复盘时单列“共同作者”清单，是信任轴的信号。

## 七、结尾提出一个具体的 ask
Demo 的第三个作用是换取权限。没有 ask，就没有可检验的信任信号。
- ask 具体到：哪份数据、哪两位使用者的多少分钟、哪个会议、什么期限。事先写进简报，现场说出口。
- 同时记下过去同类请求的等待时间，作为对照。
- 样本类 ask（“想要更多的井/文件/案件”）要写清验证目的、数量、类型和期限，说明少了它哪个结论下不了，让客户容易批。
- 失误：Demo 结束于“大家有什么问题”，没有下一步。

## 原则之间的张力

| 张力 | 取舍 |
|---|---|
| 让客户动手 vs 他会上传没测过的文件 | 保留动手；准备沙盒与失败预案；失败转为原则三 |
| 现场可改 vs 弄坏别处、被牵着走 | 边界与时限事先写；改完回归；超界就约时间 |
| 一次一个主张 vs 不挑软柿子 | 主张唯一，案例取中等难度；难例用于展示失败 |
| 留缺口 vs 不造假 | 只留真实已知的低风险缺口，禁止制造 |
| 主动展示失败 vs 第一次见面的信任脆弱 | 失败样例数量 2–3 个，配原因和想法；不展示会危及安全或合规的失败 |
