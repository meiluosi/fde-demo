# 衔接

本 Skill 可独立运行。有上游产物时手动读取，无工具或仓库依赖。记录输入路径、版本/哈希和读取日期；未提供的文件标“未提供”，不模拟读取成功；不改上游原件，只在新的场景目录引用或复制必要片段。多批输入同名编号时加命名空间（如 `framing:V2`、`ramp:S01`），保留原编号。

## 承接 fde-problem-framing

| 上游产物 | 用在 Demo 的哪里 |
|---|---|
| 定义卡“问题” | 最痛的一步，及“谁在什么任务里受损” |
| 定义卡“怎么算成功”与基线 | 价值轴的对照；基线缺失则写“待测” |
| 定义卡“本期不做” | 简报“本次不展示”和现场可改边界 |
| 验证计划 V* | 选出本次 Demo 要检验的**一条**假设；其余留待后续 |
| 证据台账 / 失败样本 | 失败样例的来源 |
| 建议结论 Investigate | Demo 是执行最小验证的载体之一，不是绕过验证的捷径 |

定义卡建议结论若为 Non-AI 或 Stop-Defer，先问清为什么还要 Demo；可能是为了展示非 AI 的改进，则按“价值判断”设计，不展示 AI。

## 承接 fde-ramp

| 上游产物 | 用在 Demo 的哪里 |
|---|---|
| activities.md / flow.md | 选最痛的一步，确认使用者角色 |
| corrections.md | 已被一线改过的流程；Demo 的叙述必须使用改后版本 |
| glossary.md | 用客户自己的词讲，不用我们的词 |
| 一线联系人 | 观众中的使用者 |
| sources / verification-list | 未决问题可转为现场要听的话 |

## 回写上游

Demo 后可能推翻的内容，写回上游而不是只留在复盘里：
- 被推翻或修改的假设 → 定义卡与验证计划（交给 fde-problem-framing 的复盘/修订流程）。
- 客户现场纠正的流程、角色、术语 → 活动表与行话表（交给 fde-ramp 的修订）。

## 交给后续阶段

试点阶段见 fde-pilot（草案，未经使用验证）。系列约定见 [series.md](series.md)。Proceed 的复盘应带出这些字段，供下一阶段直接使用：
- 已换到的授权与对接人；尚未拿到的授权；
- 三轴各自仍未验证的假设；
- 失败样例清单（转为试点护栏和停止条件）；
- 共同作者清单（可能的支持者）与反向信号清单（需处理的阻力）；
- 现场提出的需求变更。
