# 回溯复盘

对已经发生的 Demo 做事后整理。它服务两个目的：校准本 Skill 的模板与规则是否贴合真实场景；沉淀可匿名化的案例。它**不是**对当时决策的重新裁定。

## 限制
- 所有记录来自回忆，按“转述”处理。各轴最高判“部分”，不得判“已验证”，结论不得判 Proceed。
- `scripts/check_debrief.py --retro` 会把这两种情况报为错误，并要求复盘里写明“复盘类型：回溯”。
- 如果手上有当时的书面材料（审批邮件、系统日志、录屏、纪要、PPT），它们比回忆强：能当作原记录的，按原类型进记录表并在备注写文件名，然后走正常复盘，不加 `--retro`。只有回忆的部分仍按转述。
- 事后知道项目结局（成了或黄了），必须单列，不能倒推当时的证据。

## 做法
1. 选一个具体的 Demo，先确认匿名化和可否进入仓库、书稿的范围。
2. 用[访谈提纲](../templates/retro-interview.md)逐节回忆，由你或助手提问。助手只记录回答，不补全没说过的内容。
3. 整理成[记录表](../templates/session-log.md)，每条在备注写来源：回忆 / 当时笔记 / 当时邮件 / 他人转述。
4. 按[复盘报告](../templates/debrief.md)判轴，复盘类型写“回溯”。
5. 写[适配报告](../templates/retro-fit-report.md)：这是主要产出。逐项记录模板字段哪些多余、缺失、难填，规则（阈值、证据要求）哪些过严或过松，事前登记缺失带来的偏差，以及需要修订 Skill 的条目。
6. 把适配报告里的修订写回 DEVELOPMENT.md，并把匿名化后的案例作为新示例或测试。

## 记法
- 回忆里“客户认可某点”但没有原话：记为具体言语（若指向具体事实）或泛泛言语，在记录里写“回忆，无原话”。
- 作者的事后自评（如“现在看技术被高估”）记为解读，不入证据，但进适配报告。
- 客户对我们提出的期待（更准、更多规范）记为价值轴的具体言语；只有授权、数据、人员、会议这类给予才进信任轴。
- 回忆里没有的信息写“未提供”，不推测。

## 回溯中的偏差与对策
| 偏差 | 表现 | 对策 |
|---|---|---|
| 后见之明 | 知道结局后觉得当时的信号“明显” | 只写当时已有的信息；结局单列 |
| 幸存者偏差 | 只记得成功的 Demo | 同时回溯一个不顺利的 |
| 记忆美化 | 客户反应被记得更积极 | 要求原话和行为，没有就标“仅回忆” |
| 归因偏差 | 把成功归于 Demo，忽略同期别的事 | 写出其他可能原因 |
| 事前登记缺失 | 当时没写成败信号 | 如实写“无事前登记”，不得事后补登；适配报告里记为模板价值证据 |

## 产出的边界
回溯得到的是对 Skill 的修订依据和案例素材，不是对当时项目的评分。涉及客户、人员和数据的内容在进入公开仓库或书稿前，先匿名化并确认授权。
